## Память и производительность

Подтверждённой утечки Python-кучи аудит не установил. Исправлены конкретные риски:
неограниченные ожидания Redis/брокера, отсутствие явного освобождения ресурсов,
блокировка event loop и частичная запись PDF. Тесты проверяют возврат соединений в
пул на успешных и ошибочных путях, параллельное создание PDF и удаление временных
файлов при сбоях save/fsync/replace. Это не заменяет длительный production soak
с наблюдением RSS и нагрузкой реального профиля.

Диспетчер получает не больше 100 записей, дашборд материализует не больше 10
сессий, JSON ограничен 16 КиБ; денежная арифметика использует Decimal. Пулы и
конкурентность имеют явные верхние границы. Блокировка одного устройства сохраняет
финансовую последовательность, разные устройства на PostgreSQL не требуют общей
блокировки. SQLite сериализует writers и предназначен для разработки.

Не заявляется численное ускорение относительно исходной версии: исходный API не
имел рабочего DB dependency, сопоставимого бенчмарка не было. Точные агрегаты и
сортировка dashboard на большой БД потребуют summary tables/кэша. Финансовые PDF,
ledger/outbox и логи занимают диск: политика хранения, архивирования и мониторинг
остаются обязанностью оператора. Удаление ledger ограничивает гарантию защиты от
повторных запросов, поэтому автоматическая очистка не включена.

## Проверки

В облачной машине использован CPython 3.14.8, SQLite и настоящий PostgreSQL 18,
Redis 7, отдельные процессы Uvicorn/Django/Celery worker+beat.

- `pytest`: **170 passed**, без skipped, включая PostgreSQL concurrency и миграции.
- Отдельный Django runner: **23 passed**.
- Покрытие API с учётом ветвей: **95%**. Покрытие не доказывает полноту всех edge cases.
- Ruff lint/format, `git diff --check`, Django system checks и migration consistency — passed.
- Alembic fresh/legacy migration, parity, повторный запуск и отказ при опасных
  данных — passed. Исходная SQLite-база проверялась только на закрытой временной
  копии; количества финансовых и Django-записей сохранены.
- Celery не инициализирует Django по глобальному `DJANGO_SETTINGS_MODULE`; проверен отдельный subprocess с посторонней конфигурацией.
- Реальный Redis rate-limit smoke: `200, 200, 429` при лимите 2/minute; liveness остаётся доступным.
- Реальный HTTP smoke: readiness/OpenAPI/docs, Django login/static assets, start →
  charge → identical replay → balance → close; outbox выполнен worker, PDF проверен.
  Синтетические финансовые записи после проверки удалены.
- `pip-audit`: **0 известных уязвимостей** в 89 внешних зависимостях на дату проверки.
  Собственный проект не опубликован на PyPI и проверен исходниками, а не advisory DB.

Покрыты конкурирующие начисления/старты/повторы, конфликт ключа, ошибки commit,
отказ брокера/диска, lease recovery, повторная доставка, невалидные/граничные суммы
и timestamps, inactive/unknown devices, неверные ключи, безопасные ошибки,
авторизация и read-only admin, unavailable Redis/БД, миграция legacy UUID.

Есть предупреждения upstream: Starlette рекомендует `httpx2` для своего TestClient,
SlowAPI использует deprecated `asyncio.iscoroutinefunction` (удаление ожидается в
Python 3.16). На Python 3.14 эти проверки проходят; warnings не подавлены.

## Требования перед production

1. Если пароль superuser из исторической SQLite-базы или встроенные Django secrets
   использовались в реальной среде, замените их и инвалидируйте затронутые сессии.
   Удаление файлов не удаляет историю Git. Сами значения в отчёт и логи не копировались.
2. API key даёт доступ доверенному шлюзу одной организации. Индивидуальная
   авторизация устройств/арендаторов, mTLS, управление ключами и provisioning не
   реализованы; не выдавайте общий ключ недоверенным устройствам.
3. HTTPS, закрытые Redis/БД, резервные копии, мониторинг outbox/storage, retention
   и production process supervisor обязательны. Локальные серверы разработки
   не являются production deployment.
4. Миграция существующей базы требует проверенной резервной копии и остановки
   writers. См. [руководство миграции](migrations/README_RU.md); неизвестная/опасная
   схема приводит к отказу, а не к удалению или переписыванию задолженности.

Настройка текущей машины и сохранение draft конфигурации не означают публикацию
облачной среды или подтверждённое восстановление в новой задаче.
