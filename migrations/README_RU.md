# Миграции базы данных приложения

Язык: [English](README.md) | **Русский** ·
[Руководство проекта](../README_RU.md) · [Отчёт аудита](../AUDIT_RU.md)

Alembic управляет таблицами `device`, `usagesession`, `usageevent` и
`invoiceoutbox`. Django управляет своими таблицами аутентификации, сессий и
админки; его модели биллинга — неуправляемые проекции только для чтения.
Выполняйте команды из корня репозитория в существующем checkout. Облачные задачи
уже используют изолированные рабочие пространства; не создавайте дополнительный
Git worktree для настройки.

## Новая база данных для разработки

Используйте Python 3.14 и lockfile из репозитория:

```bash
uv sync --frozen --extra dev
uv run --frozen --extra dev alembic upgrade head
uv run --frozen --extra dev python admin_panel/manage.py migrate --noinput
uv run --frozen --extra dev alembic check
```

Приложение и Django читают `DATABASE_URL` из одного окружения или `.env` в корне
проекта. По умолчанию база находится в локальном каталоге состояния, вне
отслеживаемых файлов приложения. Для PostgreSQL используются URL вида
`postgresql+psycopg://`; для SQLite — `sqlite:///relative/path.sqlite3` или
`sqlite:////absolute/path.sqlite3`. Передавайте учётные данные через настройки
среды; никогда не коммитьте их и не записывайте в `alembic.ini`. В production
необходимо выполнить и остальные требования к конфигурации приложения, включая
ключ API. В production `AUTO_CREATE_SCHEMA` должен оставаться false:
`create_all()` не умеет изменять существующие таблицы.

Начальная ревизия содержит явный DDL и не вызывает
`metadata.create_all()` приложения. Команда `alembic upgrade head --sql`
формирует SQL для новой базы; проверка и принятие существующей схемы требуют
живого подключения.

## Существующее развёртывание: резервная копия, проверка, миграция

1. Создайте резервную копию **фактической базы данных приложения** и проверьте,
   что она восстанавливается. Ранее закоммиченный `admin_panel/db.sqlite3` —
   раскрытый артефакт разработки, а не база развёрнутого приложения или
   безопасный источник учётных данных. Замените любые учётные данные, взятые из
   него. Никогда не выполняйте миграции над отслеживаемым файлом во время
   настройки; для репетиции используйте отдельную восстановленную копию.
2. Остановите процессы API, обработчики счетов, планировщики и любые другие
   процессы, записывающие данные в БД. Сначала направьте `DATABASE_URL` на
   восстановленную копию для репетиции. Убедитесь, что после развёртывания FastAPI
   и Django будут использовать одну и ту же целевую базу.
3. Выполните `alembic current`, затем `alembic upgrade head`. База без версии,
   содержащая в точности распознаваемые старые таблицы приложения `device` и
   `usagesession`, принимается автоматически. Посторонние таблицы
   аутентификации и админки Django остаются без изменений. Выполнять
   `alembic stamp` не требуется.
4. Сверьте количество сессий, сумму существующих `total_cost` и выборочные
   идентификаторы устройств/сессий с резервной копией. Выполните `alembic check`,
   затем команды Django `migrate --noinput` и `check`. Проверьте биллинг и чтение
   дашборда до повторения процедуры на базе развёрнутого приложения, для которой
   создана резервная копия.

Миграция сохраняет все сессии, суммы задолженности, флаги активности и
существующие timestamps создания. Отсутствующие значения `created_at`
заполняются единым моментом UTC начала миграции; эти значения отражают время
миграции, а не восстановленное историческое время события. Отсутствующий
`last_ping_at` остаётся null. Старые PostgreSQL timestamps без часового пояса
интерпретируются как UTC в соответствии с прежней настройкой `USE_TZ=True`.
Проверьте это предположение по истории развёртывания.

Идентификаторы сессий становятся строками длиной до 36 символов. Значения
нативного типа UUID в PostgreSQL преобразуются в каноническое текстовое
представление. Существующие 32-символьные UUID-строки SQLite сохраняются в
точности, как и существующие строки с дефисами. Новая проекция Django на основе
`CharField` поддерживает оба варианта. Проверьте интеграции, рассчитанные на
прежний нативный тип UUID в БД. Старый одноколоночный индекс устройства сессии,
созданный Django, заменяется новым индексом `(device_id, created_at)`, который
сохраняет этот префикс поиска. Новые таблицы журнала идемпотентности и outbox
счетов изначально пусты: миграция не может восстановить исторические ключи
идемпотентности и не создаёт и не отправляет повторно старые счета.

Миграция отказывается продолжать при наличии нескольких активных сессий одного
устройства, отрицательных/слишком больших/избыточно точных денежных значений,
отсутствующих обязательных значений, невалидных UUID сессий, сессий без
существующего устройства, пользовательских check constraints, неожиданных
зависимостей по внешним ключам, неполного набора таблиц приложения или неизвестной
схемы. Сохраните резервную копию и устраните конкретную проблему данных/схемы
отдельным проверенным изменением; затем повторите попытку. Не устраняйте
дублирующиеся сессии удалением строк или списанием их задолженности. Не
используйте `stamp head` для обхода проверок. Для базы, ранее созданной
современным `create_all()`, также требуется явная проверенная процедура
установления исходной версии; соответствие такой базы этой ревизии намеренно
не предполагается автоматически.

Пересоздание таблиц SQLite выполняется в настоящей транзакции с проверкой
согласованности внешних ключей до и после операции. PostgreSQL использует
транзакционный DDL. Некорректные старые данные проверяются до изменения таблиц
приложения. Выполняйте миграцию при остановленных процессах записи; валидация
не заменяет окно технического обслуживания.

## Откат и будущие изменения

Начальная ревизия намеренно запрещает автоматический downgrade: удаление
журнала/outbox уничтожило бы записи биллинга и защиты от повторных запросов.
Восстановите проверенную резервную копию или подготовьте проверенную миграцию
вперёд с сохранением данных. Согласовывайте версии развёртываемого кода
приложения и схемы БД.

Для будущих изменений схемы создайте и проверьте явную ревизию:

```bash
uv run --frozen --extra dev alembic revision --autogenerate -m "describe change"
uv run --frozen --extra dev alembic upgrade head
uv run --frozen --extra dev alembic check
```

Автоматическая генерация создаёт черновик: проверьте сохранность данных,
блокировки, заполнение существующих строк, совместимость с SQLite и поведение
как при применении, так и при откате. Сгенерированная миграция не должна удалять
существующие таблицы, которыми управляет Django.
