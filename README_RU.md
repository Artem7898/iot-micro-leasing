# IoT Micro-Leasing 2

[English (основной)](README.md) | **Русский**

Платформа учёта использования IoT-оборудования: FastAPI, транзакционный биллинг,
Django back office и генерация PDF через Celery. Python **3.14**, Django **5.2 LTS**,
точные суммы `Decimal`, воспроизводимые зависимости в `uv.lock`.

## Разработка

Используйте существующий checkout. Облачная задача уже изолирована; дополнительный
Git worktree для настройки не нужен.

```bash
uv sync --frozen --extra dev
cp .env.example .env  # только если собственного .env ещё нет
# Redis обязателен для ограничителя запросов и фоновых задач:
docker compose up -d redis
uv run --frozen alembic upgrade head
uv run --frozen python admin_panel/manage.py migrate --noinput
```

SQLite хранится в `.local/state/dev.sqlite3`. FastAPI и Django используют одну
`DATABASE_URL`; задайте абсолютный `IOT_STATE_DIR`, если запускаете команды из
разных каталогов. PostgreSQL поддерживается через `postgresql+psycopg://`.
Контейнер PostgreSQL опционален: перед запуском передайте `POSTGRES_PASSWORD`
через защищённое окружение. PostgreSQL не инициализируется с пустым паролем;
для запуска только Redis пароль PostgreSQL не нужен.

В отдельных терминалах из корня проекта:

```bash
make run-api
make run-admin
make run-worker
make run-beat
```

API слушает порт 8000, Django — 8001; оба привязаны к loopback. Документация API:
`/api/docs`; вход в back office: `/admin/`; операционный дашборд:
`/admin/redis-metrics/`. Для личного входа создайте учётную запись командой
`uv run --frozen python admin_panel/manage.py createsuperuser`. Пароли не входят в
репозиторий или инструкции среды. `runserver` предназначен для разработки.

`.env.example` явно отключает API-аутентификацию **только для локальной разработки**.
По умолчанию код требует `X-API-Key`; отсутствие настроенного `API_KEY` приводит к
503, неверный ключ — к 401. Для production обязательны `ENVIRONMENT=production`,
PostgreSQL, `API_AUTH_ENABLED=true`, защищённый `API_KEY` длиной не менее 32 символов,
`DJANGO_DEBUG=false`, сильный `DJANGO_SECRET_KEY` и явный `DJANGO_ALLOWED_HOSTS`.
Публикуйте через HTTPS reverse proxy и production WSGI/ASGI server; Redis и БД не
должны быть доступны из Интернета. Ключ API предназначен доверенному шлюзу одной
организации: пользовательская/арендаторская авторизация и mTLS устройств требуют
отдельного проектирования. Не передавайте общий ключ недоверенным клиентам.

## Поведение API

`POST /api/v1/usage/ping` требует уникальный `Idempotency-Key` (1–128 печатных ASCII
символов). При повторе передавайте **тот же ключ и тот же payload**, включая
исходный timestamp. Ответ сохранён в БД: повтор не увеличивает задолженность;
повторное использование ключа для другого события возвращает 409. Ключи глобальны
в пределах экземпляра платформы.

```json
{
  "device_id": "dev_printer01",
  "event_type": "usage_tick",
  "timestamp": "2026-10-18T12:00:00+00:00",
  "payload": {"units_consumed": "10.0000"}
}
```

Сначала зарегистрируйте устройство через доверенный provisioning-процесс и
отправьте `session_start`; завершите работу событием `session_end`. Дашборд
намеренно не изменяет финансовые записи. События должны иметь timezone, отставать
не более чем на 300 секунд и не приходить из будущего. Порядок событий внутри
сессии монотонный; равные timestamps допускаются для разных событий.
`usage_tick` требует положительное потребление; остальные события допускают ноль.
Потребление ограничено 1e9 и четырьмя десятичными знаками; JSON — 16 КиБ. Лишние
поля, отрицательные числа, bool, NaN/Infinity отклоняются. Долг сессии ограничен
`99999999.9999`; округление — half-even до четырёх знаков. Денежные ответы —
**строки**, например `"5.0000"`, без преобразования во float.

Открытие второй активной сессии, конфликт ключа, нарушение порядка событий или
переполнение суммы возвращают 409; неизвестное устройство — 404, отключённое —
403, ошибка входных данных — 422. При временной ошибке БД (503) повторяйте запрос
с прежним ключом. Ошибки не содержат исходного payload или текста внутренних
исключений. `X-Request-ID` связывает запрос со структурированными логами.

## Архитектура и надёжность

- Синхронные SQLAlchemy/SQLModel Sessions работают в thread pool FastAPI и всегда
  закрываются. Транзакция блокирует строку устройства до чтения/изменения баланса;
  SQLite сериализует записи. Уникальный частичный индекс разрешает одну активную
  сессию на устройство. Финансовые ограничения дополнительно проверяются БД.
- Закрытие сессии, replay-receipt и запись invoice outbox фиксируются вместе.
  Отправка в Redis происходит после commit. Worker записывает PDF атомарно, затем
  подтверждает `completed_at`; незавершённая доставка повторяется через 10 минут.
  Celery beat обязателен для восстановления после сбоев. Доставка at-least-once;
  PDF-обработчик допускает повторы и параллельное выполнение.
- Alembic владеет финансовой схемой; Django — таблицами пользователей и админки.
  Финансовые Django-модели unmanaged и read-only. Для существующих БД выполните
  [инструкции миграции](migrations/README_RU.md), сначала на восстановленной копии.
- Общий Redis-backed rate limiter не переключается молча в память при отказе
  Redis. `/health` проверяет жизнь процесса; `/ready` проверяет Redis, соединение
  БД и наличие актуальных таблиц/колонок.
- Дашборд показывает реальные суммы/сессии/устройства и метрики Redis, ограничивает
  выдачу десятью последними сессиями, закрывает Redis-соединения и имеет таймауты.
  Ошибки сервисов отображаются без внутренних деталей. На больших объёмах точные
  агрегаты следует переносить в summary tables или кэш.

PDF, журналы и idempotency ledger требуют политики хранения и мониторинга диска.
Автоматическое удаление финансовых данных намеренно не включено: срок хранения и
гарантированный период защиты от повторов должен определить оператор.

## Проверки

```bash
make lint
make run-tests
uv run --frozen --extra dev pytest --cov=api --cov-report=term-missing
uv run --frozen --extra dev pip-audit --local
uv run --frozen alembic check
uv run --frozen python admin_panel/manage.py makemigrations --check --dry-run
```

Unit-тесты изолируют Redis и используют временные БД. Для реальных проверок
конкурентности и миграций PostgreSQL укажите `TEST_POSTGRES_URL`; каждый тест
использует собственную временную схему. Без этой переменной только PostgreSQL
проверки отмечаются skipped. GitHub Actions проверяет обе базы.

Список обнаруженных дефектов, исправлений и границ проверки:
[отчёт аудита](AUDIT_RU.md).

## Защита ветки

Основная ветка — `master`. Политика
[.github/branch-protection.json](.github/branch-protection.json) требует pull
request, успешные проверки `python` и `postgres` на актуальной ветке, разрешённые
обсуждения и линейную историю. Force push и удаление запрещены; правила действуют
также для администраторов. Обязательное одобрение второго участника отключено,
чтобы репозиторий мог сопровождать один разработчик.

При доступном GitHub API и правах администрирования репозитория выполните:

```bash
bash .github/protect-master.sh
```

Скрипт сначала проверяет состояние GitHub, сохраняет существующую защиту или
rulesets и проверяет применение новой политики. Сам коммит файла политики не
включает защиту ветки. В среде должен быть разрешён `api.github.com`; не сохраняйте
токены в отслеживаемых файлах или аргументах команд.
